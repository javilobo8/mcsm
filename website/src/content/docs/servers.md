Everything about a single Minecraft server lives on its page: open **Servers** in the sidebar and click a server. This guide covers creating one, changing its configuration and operating it day to day.

## Create a server

1. Click **New server** in the sidebar (or the button on the Servers page).
2. **Template or from scratch.** Pick a template, or **From scratch** to choose the type, version and mods yourself. Everything else can be adjusted later in Configuration.
3. **Node and name.** Choose the node, give the server a name (up to 60 characters), optionally a game port, and decide whether it should **Start on creation**. An empty port means "automatic".
4. **Review.** Check the summary and create the server.

![The wizard's review step](/screenshots/02-wizard-review.webp)

The panel gives new servers a port from its range (25565 up to 25600 by default; see [Settings](/docs/settings)). Repeated names get a suffix in their autogenerated slug (`-2`, `-3`, and so on). Each server runs in a container named `mcsm-<slug>`, and its world lives in `DATA_ROOT/<slug>/data` on the node.

> [!TIP]
> The first server on each node gets port 25565, which is also mc-router's default. If you plan to use the [router](/docs/router), enable it before creating servers on that node.

## Types, versions and builds

In **Configuration → Version and mods** you pick the **Type**:

| Group | Types |
|---|---|
| Vanilla | Vanilla |
| Plugins | Paper, Purpur, Spigot, Folia |
| Mods | Fabric, Forge, NeoForge, Quilt |
| Modpacks | Modrinth modpack, CurseForge modpack, FTB modpack |

Then choose the **Minecraft version** from the list or type one (`LATEST`, `SNAPSHOT` or a version like `1.21.4`), and the **Java (image tag)**: `java21`, `java25`, `java17`, `java8` or `latest`.

![Choosing a Minecraft version](/screenshots/01b-selector-version.webp)

The version and build lists come from the official sources over HTTPS and are cached in memory (1 hour for versions, 15 minutes for builds). Without Internet access from the panel you can type the version by hand. See [Versions and builds](/docs/settings#versions-and-builds) for the list of sources.

The **Build / loader** field pins the build or loader version for Paper, Folia, Purpur, Fabric, Quilt, Forge and NeoForge. Empty means the latest at startup. A value needs a type that has builds and a concrete version, and only stable builds of Paper and Folia are offered.

Depending on the type, the same section lets you add:

- **Mods:** Modrinth projects, CurseForge files and `.jar` URLs.
- **Plugins:** Modrinth projects, Spiget resources and `.jar` URLs.
- **Modpacks:** the pack slug or URL, its version and an optional loader.

CurseForge modpacks and files need an API key, which you save in [Settings](/docs/settings#curseforge-api-key).

## Configure a server

The **Configuration** tab is a sectioned form that edits the server's definition:

| Section | What it holds |
|---|---|
| General | Name, slug and container name, the RCON password (hidden until you reveal it), the RCON address if the server publishes it, and **Save as template** |
| Version and mods | Type, version, build, Java, mods, plugins and modpacks |
| Properties | Common `server.properties` values (MOTD, difficulty, game mode, max players, view distance and more) |
| Players | Whitelist and operators |
| Network | Game port, extra ports (for example Geyser's `19132/udp`), the router hostname and **Publish RCON** |
| Resources | JVM memory, container RAM limit, CPU limit and restart policy |
| Advanced | Extra environment variables, one `KEY=value` per line |

![The Configuration tab](/screenshots/05-configuration.webp)

Changes are not applied as you type. Click **Review and apply** to see what will change. If the change needs it, the container is recreated and the server restarts; the world is not touched.

A few rules the form enforces:

- JVM memory looks like `4G` or `512M`. Without an explicit RAM limit, the container is limited to the JVM memory plus 1 GiB.
- Environment variable names must match `^[A-Za-z_][A-Za-z0-9_]*$`, and some are reserved because the panel generates them.
- Extra ports cannot use the container port 25575: RCON is published only with **Publish RCON**.
- Whitelist and operators lists generate their own variables, so you cannot also set those in the environment.
- A server definition is capped at 64 KiB once serialized.

> [!NOTE]
> If a node is offline when you apply a change, it shows as pending and is applied when the node returns.

## Console and commands

The **Console** tab streams the server's log live. Type a command at the bottom without the leading slash (`list`, `say hello`, `whitelist add Lobo`); the up and down arrows walk through your command history. A filter box narrows the lines shown.

Commands travel over RCON on the internal Docker network, and the console hides the RCON password and the CurseForge API key.

### Publishing RCON

By default a server's RCON is only reachable from the agent, over the internal Docker network. To use another RCON client (from your LAN, or from the Internet if you forward the port), turn on **Publish RCON** in **Configuration → Network**. The panel assigns a free port from the panel's port range, like the game port, and you can change it. Applying the change recreates the container.

The dashboard shows `RCON <host>:<port>` under the address of every server that publishes it, and the General section shows the RCON address next to the password. The host is the one in **Settings → Connection address**.

- Each server needs its own port: mc-router cannot route RCON, because the protocol carries no hostname. A server behind the router still publishes RCON on its own port.
- RCON is not encrypted: the password and the commands travel in clear text. The panel generates a long random password (an imported server keeps the container's own RCON password, which can be weak), and anyone on the path of the connection can read it. Prefer to keep it on the LAN.
- A server asleep under the router's autoscale does not answer RCON, and an RCON connection does not wake it.
- Templates do not carry the RCON port. When a server migrates to a node where its RCON port is taken, it gets another free one and the migration tells you which.

## Power actions

The buttons in the server header act on the server's *desired state*:

| Button | What it does |
|---|---|
| Start | Starts a stopped server. |
| Stop | Stops it cleanly. |
| Restart | Stops and starts it. |
| Kill | Kills the process without saving. This can corrupt the world, so the panel asks to confirm. |

The buttons are disabled while the node is offline. Start and stop also report a conflict while a backup, restore or migration has the server reserved. See [Backups](/docs/backups#space-files-and-simultaneous-jobs) and [Migration between nodes](/docs/migration).

A server that exits with an error more than 3 times in an hour is stopped and not restarted until you press **Start**. See [Crash loops](/docs/events#crash-loops).

## Connection address

The server header shows the address players type in Minecraft, and under it the server's own port. The address comes from [Settings → Connection address](/docs/settings#connection-address). Servers that join through mc-router show their hostname with the router's port (or the external port you configured).

## Overview and metrics

The **Overview** tab shows the player count, detected version, uptime, latency, container ID, healthcheck, last exit code, and which configuration version is applied. Below, charts for the last **1 hour, 24 hours or 7 days** show players, CPU (100 % = 1 core), memory and, on Paper and Purpur, TPS.

Metrics are collected every 10 seconds while the server runs. There is no data for periods when it was stopped.

## Templates and copying a server

A template stores all of a server's configuration except its name, ports and RCON password. Create them in **Templates**, or use **Save as template** in a server's General section. From **Templates** you can edit, duplicate or delete them, and create a server from one.

A template includes the backup schedule, so every server created from it inherits that schedule. Change it per server in the Backups tab.

To make a copy of an existing server's setup, save it as a template and create a new server from it. This copies the configuration, not the world. To move a world, use a [backup](/docs/backups) or [migration](/docs/migration).

## Delete a server

Use the trash button in the header. The dialog has a checkbox, **Also delete the world and files**, which removes the server's data from the node and cannot be undone. Without it, the data stays in `DATA_ROOT/<slug>`.
